# План улучшений: Рабочая карта обследования EXPERTUS

Документ описывает текущую логику заполнения шаблона, выявленные проблемы и пошаговый план улучшений — чтобы документ был **красивым, чётким, понятным** и **стабильно работал**.

---

## 1. Как сейчас пополняются шаблоны (анализ)

### 1.1 Два механизма заполнения

| Механизм | Где работает | Как устроен |
|----------|--------------|-------------|
| **Плейсхолдеры `{{key}}`** | Параграфы, ячейки таблиц, колонтитулы | В тексте ищется строка `{{inspector_name}}`, `{{customer}}` и т.д. и заменяется значением из payload. Один плейсхолдер — одно поле. |
| **Прочерки в XML** | Файл `word/document.xml` внутри .docx/.dotx | Регулярка ищет теги `<w:t>_____</w:t>` (5+ подчёркиваний). **Порядок замены жёстко задан в коде** (customer → object_name → location → …). Первый блок прочерков получает «Заказчик», второй — «Наименование объекта» и т.д. |
| **Прочерки по правилам (FILL_BLANKS_RULES)** | Текст параграфов через python-docx | В параграфе ищется триггерная фраза («Заказчик», «Наименование объекта…» и т.д.). Текст разбивается по блокам из 3+ подчёркиваний; в эти блоки по порядку подставляются значения из списка ключей для этого правила. |

### 1.2 Откуда берутся данные

- **API:** `POST /api/v1/inspections/generate-card` принимает JSON (`InspectionCardGenerate`).
- **Схема** (`backend/app/schemas/inspections.py`): поля `inspector_name`, `inspection_date`, `customer`, `object_name`, `location`, `inventory_number`, `factory_number`, условия (температура, влажность, освещённость), оборудование (ВИК, пенетранты, дефектоскоп, толщиномер, твердомер), `documentation_state`, `defects_notes`, `sketch_note`.
- **Сервис** (`inspection_card_service.py`): из payload строится словарь замен `{{key}}` и словарь `values_by_key`; для прочерков в XML используется **фиксированный порядок** из `_ordered_values_for_xml_fill()`.

### 1.3 Специальная логика

- **Ф.И.О. исполнителя:** если в payload пусто — в API подставляется из `current_user` (full_name / email), иначе «Исполнитель».
- **Состояние документации:** в шаблон подставляется не сырое значение, а строка с отметкой одного из вариантов: «удовлетворительно [x]», «неудовлетворительно [x]», «отсутствует/ не предоставлена [x]» (`documentation_line`).
- **Примечания по дефектам:** если `defects_notes` пустое — подставляется текст-подсказка про указание оборудования.

### 1.4 Риски текущей реализации

1. **Порядок полей для прочерков в XML** жёстко зашит. Если в «Рабочая карта обследования EXPERTUS.doc» поля с прочерками идут в другом порядке (или добавлено новое поле), значения попадут не в те места.
2. **Два способа заполнения** (плейсхолдеры и прочерки) смешаны: непонятно, какой шаблон на что опирается; при правке формы легко забыть обновить либо шаблон, либо код.
3. В **FILL_BLANKS_RULES** есть два правила для примечаний («Примечание:» и «Примечание ») — дублирование и риск путаницы.
4. Файл **Рабочая карта обследования EXPERTUS.doc** в корне проекта — бинарный .doc; без конвертации в .docx и явной разметки полей непонятно, совпадает ли порядок прочерков с `_ordered_values_for_xml_fill`.
5. Нет **единого описания**: какое поле формы соответствует какому ключу в API и в шаблоне.

## 2. Цели улучшений

- Документ: **оформление чёткое, структура ясная**, все поля заполняются предсказуемо.
- Шаблон и код: **один понятный способ** подстановки данных, без скрытой зависимости от порядка прочерков в XML.
- Поддержка: **один источник истины** (таблица «поле формы ↔ ключ») и инструкция по обновлению шаблона из «Рабочая карта обследования EXPERTUS.doc».

## 3. План улучшений (по шагам)

### Этап A. Единый способ заполнения и маппинг полей

| № | Задача | Детали |
|---|--------|--------|
| A.1 | **Определить единый способ подстановки** | Рекомендация: **только плейсхолдеры `{{key}}`** во всём шаблоне. Прочерки оставить только для обратной совместимости со старыми .doc/.dotx или постепенно убрать после перехода на .docx с плейсхолдерами. |
| A.2 | **Таблица «Поле в форме ↔ ключ в коде»** | Один документ (например, в `backend/app/templates/README.md` или отдельный FIELD_MAPPING.md): название поля в форме EXPERTUS, ключ в API/шаблоне (`{{key}}`), тип, обязательно ли, значение по умолчанию. |
| A.3 | **Синхронизировать порядок XML с маппингом (если прочерки остаются)** | Либо вынести порядок полей для `_ordered_values_for_xml_fill` в конфиг/константу с комментарием «соответствует порядку полей в word/document.xml шаблона», либо явно пометить в коде, что шаблон должен содержать прочерки строго в этом порядке. |

### Этап B. Шаблон документа (красота и ясность)

| № | Задача | Детали |
|---|--------|--------|
| B.1 | **Эталонный шаблон из EXPERTUS.doc** | Конвертировать «Рабочая карта обследования EXPERTUS.doc» в .docx (Word или LibreOffice). Сохранить как `inspection_card_template.docx` в `backend/app/templates/`. |
| B.2 | **Разметка полей только плейсхолдерами** | В местах ввода данных вставить **только** `{{customer}}`, `{{object_name}}`, `{{location}}`, `{{inventory_number}}`, `{{factory_number}}`, `{{inspector_name}}`, `{{inspection_date}}`, `{{temperature_c}}`, `{{humidity_percent}}`, `{{illumination_lux}}`, `{{equipment_vik}}`, `{{equipment_penetrant}}`, `{{equipment_defectoscope}}`, `{{equipment_thickness_gauge}}`, `{{equipment_hardness}}`, `{{documentation_line}}`, `{{defects_notes}}`, `{{sketch_note}}`. Убрать зависимость от «первого/второго блока прочерков» в XML. |
| B.3 | **Оформление** | Проверить: шрифт (например Times New Roman), размеры, выравнивание заголовков и блоков, отступы, при необходимости — таблица для полей «Наименование / Зав. №» оборудования. Сделать разделы (заголовок, реквизиты, условия, оборудование, документация, дефектная ведомость, эскиз) визуально отделёнными. |
| B.4 | **Пустые значения** | Решить отображение пустых полей: оставлять пусто или подставлять «—»/прочерк. Закрепить это в сервисе (например, в `_str()` или в `_build_placeholders`) и в README шаблона. |

### Этап C. Код и надёжность

| № | Задача | Детали |
|---|--------|--------|
| C.1 | **Упростить логику прочерков (опционально)** | Если переход на «только плейсхолдеры» выполнен, можно не заполнять прочерки в XML или оставить только для обратной совместимости и пометить в коде устаревшим. |
| C.2 | **Убрать дубли в FILL_BLANKS_RULES** | Объединить правила для «Примечание» в одно (с учётом разного написания в документе) или удалить, если все поля переведены на `{{defects_notes}}`. |
| C.3 | **Валидация и значения по умолчанию** | В схеме или в сервисе: обязательность `inspection_date` уже есть; при необходимости задать разумные умолчания для отображения (например «—» для пустых строк) и описать в маппинге. |
| C.4 | **Логирование и ошибки** | При отсутствии шаблона или ошибке подстановки логировать понятное сообщение; ответ API при ошибке генерации уже возвращает текст исключения — убедиться, что в логах есть контекст (payload без чувствительных данных). |

### Этап D. Документация и сопровождение

| № | Задача | Детали |
|---|--------|--------|
| D.1 | **Обновить README шаблонов** | В `backend/app/templates/README.md`: список всех `{{key}}` с кратким описанием, приоритет форматов (.docx / .dotx / .doc), ссылка на маппинг полей. |
| D.2 | **Инструкция по обновлению шаблона из .doc** | Пошагово: открыть «Рабочая карта обследования EXPERTUS.doc» → сохранить как .docx → заменить нужные места на `{{key}}` по таблице маппинга → положить в `backend/app/templates/` → при необходимости обновить скрипт `generate_inspection_template.py` под новую структуру. |
| D.3 | **Тесты** | Добавить тест генерации: фиксированный payload → вызов `generate_inspection_card_docx` → проверка, что в полученном .docx присутствуют ожидаемые значения (например, через разбор XML или python-docx) и нет сырых плейсхолдеров `{{...}}`. |

## 4. Краткий порядок работ

1. Составить и зафиксировать **таблицу маппинга** поле формы ↔ `{{key}}` (Этап A.2).
2. Конвертировать **Рабочая карта обследования EXPERTUS.doc** в .docx и разметить поля **только плейсхолдерами** (Этапы B.1–B.2).
3. Привести **оформление** к единому стилю и правилам пустых полей (B.3–B.4).
4. Обновить **README** и инструкцию по шаблону (D.1–D.2).
5. При необходимости упростить код прочерков и FILL_BLANKS_RULES (C.1–C.2).
6. Добавить **тест генерации** (D.3).

После этого шаблон будет однозначно соответствовать коду, документ — понятным и стабильно заполняемым, а дальнейшие изменения формы можно вносить по одному источнику истины (маппинг + README).

## 5. Рекомендации из открытых источников (актуально до 2026)

Ниже — находки из практик генерации документов и нормативов, которые можно учесть в плане улучшений.

### 5.1 Лучшие практики шаблонов DOCX (2024–2025)

| Рекомендация | Источник | Применение к карте EXPERTUS |
|--------------|----------|-----------------------------|
| **Единый формат плейсхолдеров** | Системы документооборота (Omnia, Plumsail) | Использовать один синтаксис: либо `{{key}}` (как сейчас), либо `[[PropertyName]]`. Не смешивать с «прочерками по порядку» в одном шаблоне. |
| **Защита плейсхолдеров** | Word / Content Controls | В шаблоне можно размещать плейсхолдеры внутри **Content Controls** (вкладка «Разработчик»), чтобы их случайно не удалили при правке; при программном заполнении искать элементы по **тегу** (Tag) контрола. |
| **Формат даты в шаблоне** | Шаблоны с форматированием | Поддерживать явный формат даты, например `{{ inspection_date \| dd.MM.yyyy }}` или задавать формат в коде (сейчас: `%d.%m.%Y` — уже нормально). При переходе на Jinja2-движок можно добавить фильтры даты. |
| **Колонтитулы** | Microsoft / Plumsail | Количество секций колонтитулов в шаблоне и в сгенерированном документе должно совпадать; в колонтитулах предпочтительны таблицы и границы, а не фигуры/текстовые блоки. |
| **Экранирование в XML** | docxtpl, python-docx | Значения с символами `<`, `>`, `&` нужно экранировать при записи в XML (в коде уже есть `_xml_escape`). При вводе пользователем — валидировать или экранировать на бэкенде. |

### 5.2 Альтернатива: python-docx-template (docxtpl)

- **Библиотека:** [docxtpl](https://docxtpl.readthedocs.io/) — шаблоны Word с синтаксисом **Jinja2** (`{{ variable }}`, циклы, условия).
- **Плюсы:** тот же вид плейсхолдеров `{{ key }}`, плюс условия (`{% if %}`, `{% for %}`), фильтры (дата, верхний/нижний регистр), вставка изображений, RichText. Форматирование документа сохраняется.
- **Применение:** опционально рассмотреть переход на docxtpl для генерации карты: шаблон остаётся .docx с `{{customer}}`, `{{inspection_date}}` и т.д., а сложные блоки (например, список дефектов по строкам таблицы) можно делать через `{% for %}` без ручной склейки строк в одном поле.
- **Учёт до 2026:** актуальные версии docxtpl (в т.ч. 0.20.x) поддерживают Python 3.7–3.13; документация и примеры доступны.

### 5.3 Нормативная база (РФ, актуально 2024–2026)

| Документ | Суть | Связь с рабочей картой |
|----------|------|-------------------------|
| **ГОСТ 31937-2024** | Здания и сооружения. Правила обследования и мониторинга технического состояния (взамен ГОСТ 31937-2011, с 01.05.2024). | Общие требования к обследованиям; при необходимости форму карты можно сверять с требованиями к составу и оформлению результатов обследования. |
| **ГОСТ Р ИСО 17637-2024** | Неразрушающий контроль сварных швов. Визуальный контроль (ВИК) (с 01.12.2024). | Прямо относится к ВИК и применяемому оборудованию в карте; при обновлении раздела «Оборудование» и методик можно ориентироваться на стандарт. |
| **ГОСТ Р 3.102-2024** | Единая система технологической документации. Стадии разработки и виды технологических документов. **Ввод с 01.01.2026.** | Затрагивает формы технологических/рабочих документов; имеет смысл до 2026 года проверить, что форма Ф-EXP-ДП-ИЛ-7.8-03 и состав реквизитов соответствуют требованиям к видам документов по ЕСТД. |
| **ГОСТ Р 3.301-2024** | Электронная технологическая документация. Основные положения. | Если карта будет храниться/передаваться в электронном виде — учесть требования к электронной техдокументации. |

**Рекомендация:** в README или в отдельном разделе документации указать, что форма карты ориентирована на стандарты НК и при необходимости согласована с ГОСТ 31937, ГОСТ Р ИСО 17637 и ЕСТД (в т.ч. ГОСТ Р 3.102-2024 с 2026 г.).

### 5.4 Дополнительные пункты плана (из найденного)

| № | Задача | Источник |
|---|--------|----------|
| E.1 | **Формат даты** | Явно зафиксировать в маппинге и в коде формат даты (например «ДД.ММ.ГГГГ»); при расширении — опционально параметр формата в API. |
| E.2 | **Экранирование и безопасность** | Все подставляемые строки из API экранировать для XML (уже есть `_xml_escape`); при появлении полей с HTML/разметкой — санитизация или только plain text. |
| E.3 | **Проверка соответствия нормативам** | До 2026 года сверить форму карты с ГОСТ Р 3.102-2024 (виды документов, реквизиты) и при необходимости скорректировать шаблон или описание. |
| E.4 | **Опционально: docxtpl** | Оценить переход на docxtpl для генерации карты: меньше кастомной логики прочерков, возможность циклов по дефектам/оборудованию и фильтров даты в шаблоне. |
| E.5 | **Незаполненные плейсхолдеры** | Реализовать проверку после генерации (например, как в docxtpl: `get_undeclared_template_variables`): логировать или возвращать предупреждение, если в шаблоне остались незаменённые `{{...}}`. |
