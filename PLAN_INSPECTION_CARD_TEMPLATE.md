# План: шаблон «Рабочая карта обследования EXPERTUS»

## 1. Анализ документа

Файл **«Рабочая карта обследования EXPERTUS.doc»** (ТОО «EXPERTUS», форма Ф-EXP-ДП-ИЛ-7.8-03) содержит такие поля:

| Поле в документе | Источник данных | Примечание |
|------------------|-----------------|------------|
| **Заказчик (Договор/проект)** | Ручной ввод или из проекта | Строка |
| **Наименование объекта обследования** | Объект/труба (pipe) | Из мобильного: название трубы, QR, производитель |
| **Место нахождения** | Объект/труба (location) или ручной ввод | Координаты или адрес |
| **Инв.№** | Объект или ручной ввод | Инвентарный номер |
| **Зав. №** | Объект (pipe) | Заводской номер — можно использовать `qr_code` или отдельное поле |
| **Ф.И.О. исполнителя** | **Автоматически из аккаунта** | Из профиля пользователя (проверяющий) |
| **Дата** | **Автоматически** | Дата проведения обследования |
| Температура воздуха, °C | Ввод при обследовании | Число |
| Влажность воздуха, % | Ввод при обследовании | Число |
| Уровень освещенности, лк | Ввод при обследовании | Число |
| Оборудование (ВИК, пенетранты, дефектоскоп, толщиномер, твердомер) | Справочник или ручной ввод | Наименование + Зав. № |
| Состояние рабочей документации | Выбор при обследовании | Удовлетворительно / неудовлетворительно / отсутствует |
| Дефектная ведомость / примечания | Из зафиксированных дефектов | Список дефектов по объекту |
| Эскиз, схема | Фото/чертёж | Опционально, из приложения |

**Идея:** при проведении инспекции объекта в мобильном приложении пользователь заполняет только нужные строчки; **Ф.И.О. исполнителя** и **Дата** подставляются автоматически из текущего аккаунта и даты обследования.

---

## 2. Текущее состояние в проекте

- **Мобильное приложение:** есть трубы (pipe), дефекты (defect), экран добавления дефекта по `pipeId`. В профиле хранятся `user_full_name` и `user_email` (SharedPreferences); при логине сохраняется `user_email` (AuthService). Модель `InspectionEvent` уже содержит поле `inspector`.
- **Документ:** формат .doc (бинарный). Для шаблонизации удобнее иметь .docx с плейсхолдерами или разметкой полей.

---

## 3. План реализации

### Этап 1. Подготовка шаблона документа

1. **Конвертировать документ в шаблон**
   - Сохранить «Рабочая карта обследования EXPERTUS» в формате **.docx** (если возможно).
   - Заменить заполняемые значения на плейсхолдеры, например:
     - `{{inspector_name}}` — Ф.И.О. исполнителя
     - `{{inspection_date}}` — дата
     - `{{customer}}` — заказчик
     - `{{object_name}}` — наименование объекта
     - `{{location}}` — место нахождения
     - `{{inventory_number}}` — инв.№
     - `{{factory_number}}` — зав. №
     - `{{temperature}}`, `{{humidity}}`, `{{illumination}}`
     - `{{equipment_*}}` — оборудование
     - `{{documentation_state}}` — состояние документации
     - `{{defects_list}}` / примечания по дефектам
   - Хранить шаблон на бэкенде (например, в хранилище файлов) или в ресурсах приложения.

2. **Справочник полей шаблона**
   - Составить список всех плейсхолдеров и их описание (как в таблице выше) в коде или конфиге, чтобы мобильное приложение и бэкенд использовали одни и те же имена полей.

---

### Этап 2. Данные проверяющего (автозаполнение из аккаунта)

1. **Гарантировать наличие Ф.И.О. в приложении**
   - При логине: если бэкенд отдаёт имя пользователя (full_name) — сохранять в SecureStorage/профиле.
   - Профиль: продолжать хранить `user_full_name` и `user_email`; использовать их при формировании карты.
   - При формировании карты: поле «Ф.И.О. исполнителя» всегда брать из текущего пользователя (`user_full_name`); если пусто — показывать предупреждение или подставлять `user_email`.

2. **Дата обследования**
   - При создании «обследования» фиксировать дату (и при желании время).
   - В шаблоне подставлять эту дату в поле «Дата» автоматически (без ручного ввода от пользователя).

---

### Этап 3. Модель «обследование объекта» в мобильном приложении

1. **Сущность Inspection (обследование)**
   - Связать с объектом (pipe/asset): один объект — одно обследование за выбранный выезд/сессию.
   - Поля: `id`, `pipeId` (или objectId), `inspectorId` / `inspectorName`, `date`, `temperature`, `humidity`, `illumination`, `customer`, `inventoryNumber`, `factoryNumber`, `documentationState`, оборудование (можно JSON или отдельная таблица), примечания.
   - Локальная таблица (Drift) для офлайн: например `LocalInspections` с теми же полями и `syncStatus`.

2. **Связь с дефектами**
   - У дефекта уже есть `inspectionId`. При «старте обследования» создавать запись обследования и передавать её `id` при добавлении дефектов.
   - В шаблон «Дефектная ведомость» подставлять список дефектов по этому `inspectionId`.

3. **Экран/флоу обследования**
   - Вариант A: после сканирования QR трубы — «Начать обследование» → форма с полями карты (заказчик, объект, место, инв.№, зав.№, температура, влажность, освещённость, состояние документации, оборудование). Ф.И.О. и дата только отображаются (авто), не редактируются.
   - Вариант B: отдельный экран «Новое обследование» → выбор объекта (или QR) → та же форма.
   - После заполнения пользователь добавляет дефекты (как сейчас Add Defect), затем может «Сформировать рабочую карту».

---

### Этап 4. Заполнение шаблона и экспорт

1. **Сбор данных для шаблона**
   - В мобильном приложении при нажатии «Сформировать карту»:
     - Взять Ф.И.О. и дату из аккаунта и выбранного обследования.
     - Остальные поля — из сохранённого обследования и связанной трубы (наименование, место, инв.№, зав.№ и т.д.).
     - Список дефектов — по `inspectionId` из локальной БД.
   - Отправить на бэкенд JSON с полями шаблона (идентичные плейсхолдерам).

2. **Бэкенд: генерация документа**
   - API, например `POST /api/v1/inspections/{id}/export-card` или `POST /api/v1/templates/inspection-card/generate`.
   - Принимает JSON с полями; подставляет их в .docx-шаблон (например, python-docx или библиотека замены в docx).
   - Возвращает файл (docx/pdf) или ссылку на скачивание.

3. **Мобильное приложение: скачивание/просмотр**
   - Получить файл по ответу API и открыть через share_plus / file viewer или сохранить в «Документы».

---

### Этап 5. Оборудование и справочники (опционально)

- Справочник оборудования (ВИК, пенетранты, дефектоскоп и т.д.) на бэкенде или в приложении.
- В форме обследования — выбор из справочника или ручной ввод; при экспорте подставлять в соответствующие плейсхолдеры шаблона.

---

## 4. Порядок работ (кратко)

1. Конвертировать .doc в .docx и разметить плейсхолдеры; зафиксировать список полей.
2. Backend: хранилище шаблона + endpoint генерации документа по JSON.
3. Mobile: обеспечить Ф.И.О. и дату из аккаунта/обследования; модель и экран «Обследование» с полями карты; при добавлении дефекта привязка к обследованию.
4. Mobile: кнопка «Сформировать рабочую карту» → сбор данных → запрос к API → сохранение/открытие файла.
5. При необходимости: справочник оборудования и доработка полей объекта (инв.№, зав.№) в pipe/asset.

---

## 5. Итог

- **Шаблон** — это документ с плейсхолдерами вместо конкретных значений.
- **Проверяющий (Ф.И.О.) и дата** заполняются автоматически из аккаунта и даты обследования.
- Остальные строчки пользователь заполняет в мобильном приложении в рамках «обследования объекта»; при экспорте данные подставляются в шаблон на бэкенде и отдаются готовым файлом.

Если нужно, следующий шаг — детализация по бэкенду (структура API, пример JSON) или по мобильному приложению (структура экранов и моделей).
